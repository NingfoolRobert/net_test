# 崩溃线程信息采集设计

状态：设计草案，尚未实现或执行崩溃验证。

## 1. 目标与范围

第一版在进程内捕获致命信号，采集崩溃线程的原始现场和调用栈，通过调用方注入的 lambda 交付结构化信息。

已明确的职责约束：

- `CrashHandler` 只提供 crash 信息，不格式化日志、不打开日志文件、不执行日志写入。
- 信息如何处理、格式化和输出，由调用方注入的 lambda 决定。
- 第一版只采集崩溃线程，不采集其他线程。
- 记录完成后保留致命信号退出语义，以及系统生成 core 的能力。
- 致命崩溃路径不执行业务对象析构、线程 join 或统一业务资源清理。

第一版建议使用 C++17，平台限定为 Linux/glibc、x86-64。其他架构的寄存器提取需要另行适配。以下类名、操作名和内部容量均为设计建议，尚非已实现接口。

## 2. 职责划分

| 类型 | 可见性 | 职责 | 资源所有权 |
| --- | --- | --- | --- |
| `CrashHandler` | 公开 | 安装信号处理、采集当前崩溃线程信息、调用 lambda、恢复致命退出 | 信号处理规则、接收信息的可调用对象、进程级处理状态 |
| `ThreadCrashContext` | 公开 | 管理当前线程的备用信号栈 | 备用栈内存、原备用栈配置 |
| `CrashInfo` | 公开数据结构 | 承载一次回调的结构化崩溃信息 | 固定大小的数值字段和栈地址数组 |
| 调用方注入的 lambda | 由调用方定义 | 决定信息处理及输出方式 | 输出资源由调用方管理，其生命周期必须覆盖回调使用期 |

栈展开和寄存器提取作为内部函数，不增加独立的公开类。模块中不设置 `CrashLogWriter`，不依赖 fmt、Quill 或项目日志宏。

信号处理规则是进程级资源，备用信号栈是线程级资源，因此使用两个公开类分别表达其生命周期。

## 3. CrashHandler

### 3.1 职责与操作

| 操作 | 语义 |
| --- | --- |
| 构造时注入 lambda | 在正常执行上下文中保存信息接收函数，运行期间不替换 |
| `Install()` | 准备栈采集能力，检查并安装致命信号处理器 |
| `Uninstall()` | 正常退出时恢复原信号处理规则，解除处理器对实例状态的引用 |
| 析构 | 在满足生命周期约束时兜底释放模块自身资源 |

处理的信号建议固定为 `SIGSEGV`、`SIGABRT`、`SIGBUS`、`SIGILL`、`SIGFPE`。正常停止信号 `SIGTERM`、`SIGINT` 不属于该模块的崩溃处理范围。

建议通过模板参数接收并持有 lambda，第一版不使用 `std::function`。可调用对象在安装前完成构造；信号处理期间不构造、复制或替换它。

### 3.2 生命周期契约

- 一个进程最多有一个活动实例；该限制也必须覆盖不同 lambda 类型产生的模板实例。
- 不要求业务使用全局单例，但实例禁止复制和移动，保证安装后的地址稳定。
- `Install()` 在启动工作线程前调用，`Uninstall()` 在工作线程退出后调用。
- 安装、卸载不得与崩溃处理并发；第一版不支持运行中热切换。
- 安装前检查已有信号规则。其他模块已接管目标信号时，明确失败，不静默覆盖或链式调用未知处理器。
- 安装部分失败时回滚已修改的规则；回滚异常也必须报告，不能声称已完全恢复。
- 模块活动期间，调用方不得另行替换其管理的信号规则。
- 先解除信号处理器对实例的引用，再销毁可调用对象及模块资源。

安装和卸载错误通过正常上下文中的接口报告，具体错误返回类型在实现时确定。崩溃回调不用于报告正常初始化错误。

### 3.3 不承担的职责

- 不接收日志路径、日志等级、文件大小或日志轮转配置。
- 不创建业务线程，不拥有业务 socket、共享内存或业务对象。
- 不调用应用清理函数，也不保证业务日志刷新。
- 不负责配置系统 core 存储位置和容量。

## 4. ThreadCrashContext

该类只为调用线程准备备用信号栈。正常线程入口创建对象并启用，线程正常结束时停用并销毁。

| 操作 | 语义 |
| --- | --- |
| `Enable()` | 在调用线程分配并安装备用信号栈 |
| `Disable()` | 在同一线程恢复原配置，成功后释放备用栈内存 |
| 析构 | 在同一线程、正常生命周期下执行对应释放 |

约束：

- 必须在同一线程启用、停用和析构，禁止复制和移动。
- 每个线程最多启用一个实例；已有备用栈时第一版报冲突，避免混合所有权。
- 备用栈提前分配，包含保护页，大小在初始化时满足平台要求。
- 只有成功解除对备用栈的使用后才能释放其内存；解除失败时不能释放仍被引用的内存。
- 不维护全局线程列表，不采集其他线程，不控制线程退出。

没有启用该类的线程仍可能触发进程级处理器，但处理器使用普通栈；该线程发生栈溢出时的处理能力更差。仅在主线程配置备用栈不会自动覆盖工作线程。

## 5. CrashInfo 数据契约

| 字段 | 含义 |
| --- | --- |
| `stage` | 基础现场阶段或栈采集结果阶段 |
| `signal_number`、`signal_code` | 致命信号编号和原因分类 |
| `pid`、`tid` | 进程 ID 和崩溃线程 ID |
| `fault_address`、有效标记 | 仅对有相应语义的信号记录故障地址 |
| `instruction_pointer`、`stack_pointer` | 从原始 `ucontext` 提取的 PC、SP |
| 固定大小的栈地址数组 | 当前崩溃线程的调用栈地址，建议容量为 64 帧 |
| `frame_count` | 实际采集的帧数 |
| `possibly_truncated` | 是否因达到容量上限而可能截断 |

数据结构不包含动态字符串、`vector` 或已格式化的日志文本。第一版提供原始地址，函数名和源码行号解析交给后续分析；解析时需要匹配的构建产物和正确的模块加载地址或 core，不能假设 PIE/ASLR 下的绝对地址可直接映射到源码。

原始 PC 单独保存，不能把处理器内 `backtrace()` 的第一帧直接视为业务崩溃点。

回调接收只读的 `CrashInfo`。对象及其内部数组仅在本次回调期间有效；需要保留时，复制到提前准备好的存储中，不能保存引用或内部指针供以后使用。

## 6. Lambda 注入与调用协议

### 6.1 两阶段交付

同一个 lambda 最多依次接收两个阶段的通知：

1. **基础现场阶段**：提取信号、线程 ID、原始 PC、SP 等信息后立即回调，此时尚无展开结果，`frame_count` 为零。
2. **栈采集阶段**：尽力执行 `backtrace()` 后，再回调栈信息；同时保留相同的基础现场信息。

两阶段由 `stage` 区分。先交付基础现场，是为了在栈展开失败之前给调用方保存关键数据的机会。展开返回零帧时仍可交付第二阶段，但不得伪装为完整调用栈。

栈展开卡住、再次崩溃或进程提前终止时，第二阶段可能永远不会发生。回调执行完成只表示信息已交给调用方，不表示日志已经写入或持久化。

### 6.2 执行环境与限制

lambda 在崩溃线程的信号处理器中同步执行。注入 lambda 不会改变信号安全限制。

- 回调必须声明为 `noexcept`；这只能约束异常传播，不能证明异步信号安全。
- 不得调用普通 logger、`printf`、fmt、iostream。
- 不得动态分配内存、获取互斥锁、等待其他线程或调用业务清理逻辑。
- 捕获对象及其依赖资源必须有效，直到 `Uninstall()` 完成。
- 只能使用明确适合信号上下文的操作；模板约束无法自动验证这一点。

调用方可以在 lambda 中向预先打开的文件描述符执行 `write()`，或者向预先建立的非阻塞管道写入有界记录，再交给外部进程处理。短写、`EINTR`、管道已满或接收端退出等情况由输出端明确处理；管道写入还需安排 `SIGPIPE` 的处理策略。

`write()` 的异步信号安全不代表不会阻塞，也不保证数据已经持久化到磁盘。模块不承诺任意 lambda 下的固定退出时延。

如果输出端需要调用现有普通日志库，必须另行设计信息传递到安全执行上下文的机制。仅通知同进程日志线程、随后立即终止进程，不能保证日志线程来得及处理。

## 7. 崩溃处理顺序与重入

1. 进入处理器，通过确认无锁的进程级原子状态判断是否已有崩溃处理正在进行。
2. 从 `siginfo_t`、`ucontext` 提取原始故障信息。
3. 调用 lambda，交付基础现场。
4. 尽力展开当前线程栈，使用固定容量存储结果。
5. 调用 lambda，交付栈采集结果。
6. 恢复默认信号处理，正确处理信号屏蔽，并向原崩溃线程重新触发致命信号。

再次崩溃或另一线程同时崩溃时，走最短的致命退出路径，不再次调用 lambda、不递归展开栈、不等待锁。首次报告可能因此中断，不能承诺多线程同时崩溃时报告完整。

预热后的 `backtrace()` 仍没有完整的异步信号安全保证。预热只能减少首次动态加载等风险，不能消除死锁、堆损坏和栈损坏带来的问题。

重新触发信号可能改变最终 core 中的部分上下文，因此必须提前交付最初收到的故障信息。是否实际生成 core 取决于系统配置和运行环境。

## 8. 正常退出与资源释放

| 场景 | 处理方式 |
| --- | --- |
| 工作线程正常退出 | 在线程内停用并销毁 `ThreadCrashContext` |
| 所有工作线程退出后 | 主线程卸载 `CrashHandler` |
| 卸载完成后 | 调用方才可关闭或销毁 lambda 依赖的输出资源 |
| 致命崩溃 | 不依赖 C++ 析构，操作系统回收进程私有资源 |
| 临时文件、命名共享内存及外部状态 | 由应用正常退出流程或外部恢复机制处理 |

不提供在致命信号处理器内执行的统一资源清理函数。

## 9. 待实施的验收

以下是未来实现的验收条件，尚未执行：

- 在独立子进程中触发主线程和工作线程的真实段错误，核对信号、TID 和原始 PC。
- 用已知调用链验证栈地址对应预期函数，确认不会将处理器入口误认作原始故障位置。
- 验证基础现场先于栈结果交付，零帧及达到容量上限时字段含义正确。
- 使用测试 lambda 把固定记录写入预先建立的通道，由父进程检查回调结果。
- `abort()` 后仍以 `SIGABRT` 终止，不伪装为正常退出。
- 为工作线程安装备用栈后触发栈溢出，检查基础现场交付能力。
- 验证重复安装、已有信号处理器冲突、备用栈冲突和安装失败回滚。
- 正常卸载恢复信号规则；正常线程退出释放备用栈，没有模块资源泄漏。
- 回调期间再次崩溃不会递归调用回调或无限展开；同时崩溃按降级策略终止。
- 在允许生成 core 的隔离环境中验证仍能产生 core；不把信号退出测试等同于 core 落盘验证。
